# data/sector_membership/ — 板塊歸屬證據定日登記簿（ADR 0008）

## 這是什麼

每個板塊一個檔案：`{sector}.json`，內容是一個 JSON 陣列，陣列中每個元素是一筆
「歸屬事件」（某股票在某天被加入或移出某板塊，附上證據）。

這不是「板塊目前有哪些成員」的快照，而是「歸屬判斷的完整歷史紀錄」——
成員名單永遠是從事件重新推導出來的（見下方「PIT 讀取規則」），不會另外存一份
「目前名單」而讓兩份資料彼此可能不一致。

## 鐵律（違反即視為資料完整性錯誤）

### 1. Append-only：只能新增，不得改寫或刪除既有事件

- 任何事件一旦寫入檔案，永遠留在檔案裡，不可修改、不可刪除。
- 如果判斷錯了（例如證據其實不成立），**不要刪除或修改原事件**，而是新增一筆
  `action: "remove"` 的事件把它「撤銷」，並在 `evidence_desc` 說明撤銷原因。
  這樣任何時間點的「回頭看」都能重現當時的（錯誤）判斷過程，不會被事後靜默抹去。
- `sector_membership.py` 的 `add_event()` 只會對檔案做「讀出全部事件 → append 一筆
  → 整份寫回」，程式碼裡沒有、也不應該有任何「找到某筆事件並修改/刪除」的路徑。

### 2. `effective_from >= evidence_date`：生效不得早於證據

- `evidence_date`：證據本身成立/發布的日期（例如公司法說會日期、指數公告生效日、
  新聞報導日期）。
- `effective_from`：這筆歸屬判斷「開始生效」的日期，也就是 PIT 查詢時判斷某股是否
  已屬於該板塊的分界點。
- 規則：`effective_from` 不能早於 `evidence_date`。也就是不可以「現在看到一個
  2026 年的證據，回頭宣稱這檔股票從 2024 年就已經算數」——這等於用未來才存在的
  資訊污染過去的分析，違反 PIT 精神。
- `effective_from` 可以晚於 `evidence_date`（例如證據當下發布，但認定要等到下個月
  才正式生效），但不可以早於它。
- `add_event()` 對此會做驗證，違反直接 raise `MembershipIntegrityError`，不寫入。

## 欄位說明

| 欄位 | 型別 | 說明 |
|---|---|---|
| `stock_id` | str | 股票代號 |
| `sector` | str | 板塊名稱（與檔名一致） |
| `action` | `"add"` \| `"remove"` | 加入或移出板塊 |
| `segment` | `"equipment"` \| `"component"` \| `"downstream"` \| `null` | 板塊內的角色分段，可為 null（不分段或尚未判斷） |
| `evidence_grade` | `"E1"` \| `"E2"` \| `"E3"` | 證據等級，見下方分級定義 |
| `evidence_desc` | str | 證據內容摘要（人類可讀） |
| `evidence_url` | str | 證據來源連結 |
| `evidence_date` | `"YYYY-MM-DD"` | 證據成立/發布日期 |
| `effective_from` | `"YYYY-MM-DD"` | 這筆判斷開始生效的日期（PIT 查詢分界點） |
| `recorded_at` | `"YYYY-MM-DD"` | 這筆事件被寫入登記簿的日期（審計用，非 PIT 判斷依據） |

## 證據分級

- **E1（公司自揭）**：公司本身公開揭露，如法說會簡報、年報、公司新聞稿、
  對主管機關的公告。可信度最高，因為是當事人自己承認。
- **E2（官方指數）**：官方或半官方指數編製機構將該股納入相關產業指數/概念股清單
  （如證交所、櫃買中心、指數公司的產業分類或成分股名單）。
- **E3（第三方當時存檔）**：第三方在證據當時（而非現在回溯）留下的紀錄，
  如當時的新聞報導、券商研究報告、產業調查報告。重點是「當時存檔」——
  用現在才寫的回顧文章去佐證過去某個時點的歸屬，不算 E3，因為那違反 PIT 精神
  （現在的認知不能證明過去的狀態）。

沒有絕對的「哪個等級才能用」的門檻，但等級應誠實標註，供下游（如
`market_monitor.py`／`backtest_engine.py`）依需求自行決定是否要求最低等級。

## PIT 讀取規則

- `get_members(sector, as_of)`：只看 `effective_from <= as_of` 的事件，依檔案內
  出現順序（即時間序）逐筆套用 add/remove，回傳最終仍在集合內的 stock_id
  排序清單。
- `as_of` 接受 `"YYYY-MM"`（視為該月最後一天）或 `"YYYY-MM-DD"`。
- 檔案不存在或無符合事件回傳 `[]`，不會拋錯。
- `get_member_segments(sector, as_of)`：同一股票若有多筆事件，segment 取
  `effective_from` 最新一筆（同日則取檔案內較後出現者）。
- `get_members_in_universe(sector, as_of)`：`get_members` 再與該月
  `data/snapshots/YYYY-MM/universe.json` 的 `final_pass` 取交集，避免板塊登記簿
  收錄了「已經不在客觀化 universe 篩選內」的股票（如已下市、流動性不足）。
  當月快照不存在時往前回溯最多 3 個月；仍找不到則拋出 `FileNotFoundError`
  （不會靜默回傳空集合，避免「查無快照」與「查有交集但為空」混淆）。

## 為什麼要這樣設計

板塊歸屬看似穩定，但實際上會隨時間變動（新供應商拿到訂單、舊供應商出局、
公司轉型跨入新板塊）。如果只存「現在的名單」，backtest 回測過去某個月的板塊熱度
時，會不小心用「現在才知道」的名單去分析「當時」的走勢，造成 look-ahead bias。
本登記簿透過 append-only 事件 + `effective_from` 分界，讓任何 `as_of` 時間點的
查詢都只用「當時已生效」的資訊，並強制每筆判斷都附上證據，讓歸屬判斷本身
可被追溯、可被稽核、也可被之後的更好證據修正（用新事件覆蓋，而非竄改歷史）。
